# Give every mail account one folder model under an identifier MailFathom issues, keep the source binding as an attribute of a folder, and carry every act on a mailbox through one implementation per custody phase that one resolver chooses

<!-- describes: backend/src/Domain/Folders/**, backend/src/Application/Folders/**, backend/src/Application/Mail/Mutations/**, backend/src/Application/Mail/Delivery/Filing/**, backend/src/Application/Accounts/Custody/**, backend/src/Application/Synchronization/MailboxSynchronizer.cs -->

## Context and Problem Statement

[ADR 0034](0034-holding-a-mailbox-mailfathom-alone-keeps.md) let an account hold its own mailbox and chose, for messages, one identity for every account: a stored message is its own row, and the occurrence on the source server is an optional attribute of it (its axis A, option 2). It made no such choice for folders, and what was built gives each custody phase a folder model of its own:

- `mail_folders` holds the source server's folders keyed by their alias. Each row is a **binding** of an alias to a remote path at one resolution generation (`MailFolderResolution`), not a folder: every generation of a binding is kept so that an occurrence stays attributable to the remote folder it was read from.
- `local_mail_folders` holds a held account's own hierarchy keyed by a generated identifier (`LocalMailFolderId`). Its shape — identity, parent, name, role, the source alias it was created from — is already the shape of a general folder.
- A stored message points at both: a non-null `MailFolderId` naming a binding, which it keeps on a held account long after the source stopped holding it, and on a held account a `LocalMailFolderId` as well.

A mirrored account's folder, meanwhile, is a declaration in configuration rather than a row ([ADR 0007](0007-remote-mailbox-mutation-boundary-and-write-session.md), axes L to N): its identity at every surface is the alias it is declared under, and the alias deliberately never moves, so a folder renamed through MailFathom from `Projects` to `Clients` is still called `Projects` by every client and every tool.

Two consequences follow, and issue 2580 is the feature that removes both.

**The read side ignores a held account's folders.** The folder tree (`MailFolderDirectoryReader`), listing, search, `ask_mail`, and every other folder-scoped query filter on the binding's alias (`AccountScopedMailFolders`). A folder created on a held account appears only under the client's `/managed-folders`, and a message moved there is still listed, searched, and answered from in the folder it was synchronized into. The MCP tools name a folder by alias or by role, so they cannot name a folder a held account created at all, because it has no alias.

**The act side decides the phase in six places.** What a caller sees as one surface is dispatched by a `switch` on `MailAccountCustodyPhase` in `MailFolderEditor`, `MailboxChangeSubmission`, `MailboxDestinationResolver`, `MailboxMutationConverger`, `LocalMailFiler`, and `LocalMailFolderArrivals`. Each reads the phase through `ILocalMailFolderStore` and has to remember to branch on its own. `LocalMailFolderEditor` and `MirroredMailFolderEditor` share no contract — different identities, different outcome types — so `MailFolderEditor` translates between them, and names a folder by "an identity whose shape is not part of the contract": a local identifier on one account, an alias on the next.

ADR 0034 required that no caller branch on where a mailbox's truth lives, and the callers do not. Behind them, though, the choice is made wherever somebody remembered to make it, and the read side is the place nobody did. Issue 2577 asks for the shape that replaces both halves, so that the implementation issues beneath 2580 — 2578 for the folder model and the read side, 2579 for the acts — are written against one answer. This record is that answer. It produces no code.

**Issue 2741 reopened this record** for what the three implementations do with a person's act on a message, rather than for where the choice between them is made. As first written, the port made the choice in one place and kept three shapes behind it: a `Mirrored` account — the phase almost every account is in — opened a mutation record and changed nothing it stored until synchronization observed what the server reported back; a `Held` account committed the act in one transaction; a `Restoring` account committed it and opened the record that carries it to the source. So the common phase was the slow one: a change was invisible to search, `ask_mail`, the MCP tools, and every other device until the server had confirmed it, the client followed pending changes to cover the gap, and a sent copy was appended to the Sent folder and then downloaded back as if it had arrived. The held path, meanwhile, was the branch few accounts exercised. Issue 2748 is the feature that turns that around, and axes E to H below are its decision: every phase commits a person's act locally, exactly as `Held` does, and `Mirrored` and `Restoring` additionally carry it to the server through the converger, so the phases differ only in propagation and in who wins a conflict. The four axes above are untouched by it, and the status is still `proposed`, so this is an amendment rather than a supersession. The owner decided a number of its points outright before it was written, and the sections below record those as decided rather than weighing them again. **Axes E to H are decided here and built by the issues [More Information](#more-information) lists** — 2742 to 2745, 2749, 2739, and the client's 2746 and 2747; until each of those lands, the code keeps the shape the record described before this reopening, and the pages under `docs/` describe that shape.

## Decision Drivers

- **A held account's folders and moves appear everywhere mail is read**, exactly as a mirrored account's do. The defect is that a correct local commit is invisible, and the fix has to be one no future reader can forget.
- **The custody phase is decided in one place.** A new reader, a new act, or a new phase that silently ignores a held account is the failure being removed; a compiler error is the only reminder that cannot be skipped.
- **A folder's identity survives everything that happens to the folder**: a rename, a move in the hierarchy, a rename on the source by another client, a new resolution generation, a drain into `Held`, and a restore back to `Mirrored`.
- **A name a person or a model reads is not stale.** An identifier that still reads `Projects` after the folder was renamed `Clients` misleads both, and a model told to file into `Projects` will do so.
- **Configuration stays configuration.** An operator writes folder mappings, spam destinations, and per-folder settings against names they chose; none of that may start requiring an identifier the deployment generated. A rule is no longer configuration: [ADR 0048](0048-keeping-a-mail-accounts-rules-in-postgresql-and-changing-them-at-runtime.md) stores it under its account and holds its destination by the folder's identifier.
- **The two transaction shapes stay visible.** A mirrored folder act reaches the server before anything is written ([ADR 0007](0007-remote-mailbox-mutation-boundary-and-write-session.md)'s *never half an act*), and a held one commits in one transaction ([ADR 0034](0034-holding-a-mailbox-mailfathom-alone-keeps.md)'s option D1). A contract that hides the difference invites a held act to wait on IMAP or a mirrored one to write first.
- **A rolling upgrade runs two builds against one database**, so the schema change is additive and the older build keeps serving across it.
- **In sync means in MailFathom.** A change MailFathom holds is a change made, for the person who made it and for every other reader of the deployment. What has not reached the mail server yet is the deployment's to carry, not the person's to watch.
- **One implementation of a person's act runs on every account.** A held path that few accounts exercise is the path whose defects are found last.
- **A change a person saw is undone only when the server answered and refused it, and the person is always told.** An outage refuses nothing, and a change a person watched land is not quietly taken away.
- **The never-marks-read guarantee stays a property of the types.** Committing locally first widens who writes a stored field; it must not widen who can open a mutation record.
- **Nothing is guessed about identity.** ADR 0007 and ADR 0008 refuse to join an occurrence the server did not name, and a local-first act that creates one may not need that guess to come out right.

## Considered Options

The decision has eight axes. A and B are the folder model and are ordered — B decides which folders carry the identity A picks. C and D are the acts and are written against A and B. E to H arrived with the reopening on issue 2741 and are written against C: E decides when an act reaches stored state, F what synchronization does while it is still on its way, G what ends one the server will not take, and H how a message is filed into another account, which only E's answer makes a single act.

**A — what identifies a folder:**

1. An identifier MailFathom issues for every folder of every account; the alias stays as an attribute of the source binding and as configuration's name for the folder.
2. An immutable alias for every folder, generated for a folder MailFathom creates.
3. Both identities kept, behind a reference that is either — what `MailFolderEditor` does today.

**B — which folders are rows, and what a stored message names:**

1. Every account has folder rows — a mirrored account's maintained by synchronization as a projection of its source hierarchy, a held account's owned by MailFathom. The source binding is an optional attribute of a folder, and a stored message names exactly one folder.
2. Folder rows only for held accounts; a mirrored account keeps its bindings, and every reader unions the two by phase.
3. A database view over both tables that every reader queries.

**C — how an act on a mailbox reaches the copy that is the truth:**

1. One contract covering folder acts, message acts, and filing, implemented once per custody phase, with one resolver as the only reader of the phase.
2. One contract per act family, each with its own implementation per phase and its own resolver.
3. The switches stay, and the phase is read through one shared helper whose switch expressions the compiler checks for exhaustiveness.

**D — what is put behind that contract:**

1. The acts a caller requests, and nothing else; synchronization, the drain, the restore, and the converger stay specific to their mode.
2. Everything that touches a mailbox, background work included.

**E — when an act on a message reaches stored state on a mirrored account:**

1. In the transaction that records it, beside the mutation record the converger then carries to the server, so every phase runs one local commit and the phases with a source add the record.
2. Once synchronization observes the server, as ADR 0007 first decided.
3. Once the converger's command is answered, written by the converger rather than by synchronization.

**F — what synchronization does with an observed value on a field a change is still outstanding on:**

1. Leaves the stored field as the act wrote it, records what it observed on the outstanding change as the field's last observed value, and writes observations again once the change has ended — per field, so the rest of the message follows the server meanwhile.
2. Writes it as today, and lets the client's pending changes cover the gap.
3. Withholds every observation of the message while any change to it is outstanding.

**G — what ends a change the server does not take:**

1. The server's answer, in two classes: a permanent refusal ends the change at once, and a transient one no later than a configured window after its first refusal, fifteen minutes by default. A server that cannot be reached counts nothing and ends nothing.
2. A count of attempts, as today, with every failed attempt of the account's run counted, reached or not.
3. A deadline from the act itself, whatever the server answered and whether it was reached at all.

**H — how a message is filed into a folder of another account the same person holds:**

1. As one local commit that writes a new stored message on the destination account, carried as two mutation records — an append on the destination and a removal from the source, each converged by its own account over its own write connection — with the removal issued only once the append has completed; asked for by the person through the client alone.
2. As one record on the source account, whose converger carries both halves over both accounts' connections.
3. Refused; a person moves mail between accounts in another mail client.

## Decision Outcome

Chosen options: **A1**, **B1**, **C1**, **D1**, **E1**, **F1**, **G1**, and **H1**.

### A folder is identified by an identifier MailFathom issues, for every account

Every folder of every account carries a `MailFolderId`, a version 7 UUID minted under [ADR 0036](0036-minting-every-identifier-as-a-version-7-uuid-and-never-treating-one-as-a-secret.md), **for its whole life**. It is minted when the folder first exists in MailFathom — when synchronization first resolves a mirrored folder, when a held account creates one, when a source folder first delivers to a held account — and it survives every rename and move, a rename of the remote folder by another client, a new resolution generation, a drain into `Held`, and a restore back to `Mirrored`. Like every identifier ADR 0036 governs it is not a secret; whether a caller may read a folder is the account's authorization, never knowledge of the identifier.

The **alias stays, and keeps exactly two jobs**: it is the key a configuration declaration is written under — a folder mapping, a spam destination, a per-folder setting — and it is what a source binding is keyed by, together with its resolution generation. It is an attribute of a folder rather than its identity, present on every folder a declaration names and on every held folder a source folder created, and absent on a folder created on a held account. A declaration MailFathom writes for a folder a person created on a mirrored account still carries a generated alias, because configuration needs a key; nothing outside configuration and synchronization reads it.

Option A2 was refused for the reason the issue already gave and the drivers state: an alias that keeps its old name after a rename misleads both a person and a model, and ADR 0007 is right that the alias must not move, because the bindings and the checkpoints are keyed by it. An identifier that names nothing can be stable without lying. Option A3 is the state that produced the defect: a reference that is sometimes one thing and sometimes another is resolved correctly only by the code that remembered which.

### Every account has folder rows, and a stored message names exactly one of them

**One folder model serves every account** (option B1). A folder row carries its identifier, its account, its parent, its name, its role, its alias where it has one, and whether it is erased. On a mirrored account the rows are **a projection of the source hierarchy, maintained by synchronization**: a declaration that resolves gets a row, its name and parent follow the remote path the server reports, and a rename on the server — by MailFathom or by another client — updates the row rather than replacing it. On a held account the rows are **owned by MailFathom**, exactly as ADR 0034 describes its local hierarchy: the five protected roles, delete into the trash, the name validation, and the fixed `/` delimiter all stand, now applying to the folder rows of a held account.

**The source binding is an optional attribute of a folder.** A binding row — alias, resolution generation, remote path, hierarchy delimiter, and the synchronization checkpoint beside it — names the folder it binds, and a folder holds as many bindings as resolution generations have existed and as many as zero. A held folder whose source folder was drained keeps its binding exactly as long as anything on the source still needs finding; a folder created on a held account has none.

**A stored message names exactly one folder**, through one non-null reference to a folder row that replaces both `MailFolderId`-as-folder and `LocalMailFolderId`. The binding a message was read from becomes **part of its occurrence**: the binding reference, `UIDVALIDITY`, and `UID` are present together or absent together, which extends the check constraint ADR 0034 already placed on the latter two. On a mirrored account the message's folder is the folder its occurrence's binding binds, except while a move of it is outstanding, when it is the folder the move named and the occurrence still names where the server holds it ([axis F](#a-field-with-an-outstanding-change-keeps-the-value-the-act-wrote)); on a held account it is wherever the person or a rule put it, and the occurrence, while it stands, still says where the drain finds it on the source.

**Every reader filters on that one reference, and none of them reads the phase.** The folder tree, listing, search, `ask_mail`, threads, rules, spam, reply drafting, and every other folder-scoped query ask which folder a message is in and nothing else. A role resolves to the folder row playing it; an alias written in configuration resolves to the folder row carrying it. That is the whole of the fix for the read-side defect, and it is structural: a new query written against the model is correct for every custody phase without its author knowing custody exists.

**Placing an arrival stops depending on the phase.** A message synchronization stores goes into the folder its binding binds, and where that folder has been erased — which only a held account's own act can do — into the inbox, as ADR 0034 already rules. A binding that has no folder yet is given one in the same transaction: on a mirrored account the projection of its declaration, on a held account a folder named after the source folder, which is ADR 0034's correspondence rule. Whether an arrival is drained afterwards is the drain's question, not placement's.

**A per-folder setting is a property of the folder**, written in configuration under the folder's alias and read from the row that carries it. A folder with no alias is governed by the values a folder mapping that states none of them takes — visible to tools, embedded, classified for spam where the account classifies — because a folder a person made on their own held mailbox is ordinary mail of theirs. Setting those values per folder without an alias is not decided here.

Option B2 was refused because it is the defect generalized: every reader would union two sources by phase, and the one that forgot is the bug this record exists to close. Option B3 hides the union rather than removing it, keeps two writers with two identities beneath one name, and a view cannot carry the foreign key a stored message needs.

### Every act on a mailbox goes through one contract, implemented once per custody phase

**Acting on a mailbox has one port, `IMailboxCustodian`**, covering three families of act:

- **Folder acts**: describe which acts the account and each of its folders allow, then create, rename, move within the hierarchy, and delete.
- **Message acts**: set or clear flags and keywords, move, copy, and delete — with the preparation step that runs before the caller's transaction (resolving a destination, reading what a copy needs) separate from the commit that runs inside it.
- **Filing**: file a draft revision, give a draft up, and file a sent copy.

**It has one implementation per custody phase** (option C1): `MirroredMailboxCustodian`, `HeldMailboxCustodian`, and `RestoringMailboxCustodian`, each carrying the whole of what that phase does in one class and composing the collaborators that already do the work — the mirrored and local folder editors, the mutation records and the local state store, the copy appender and the local filer. Adding an act to the port is a compiler error until all three implement it. Each family takes and returns the same types in every phase: one folder identity, one outcome type per family, one refusal vocabulary.

**One resolver, `MailboxCustodianResolver`, is the only reader of the phase for acts**, and the only `switch` over `MailAccountCustodyPhase` outside the mode-specific background work. Reading the phase here means deciding something from it; the types that own the phase — the custody domain types, the store that persists them, and the administrative switch that changes them — hold and report it and decide no act, and stay as they are. Adding a phase is a compiler error in that one switch and a new implementation of the port. It reads the phase **inside the caller's transaction** for message acts and filing, which already commit in one, so a switch of custody cannot be judged differently by two acts in the same request. Nothing else reads the phase through `ILocalMailFolderStore`, which goes back to being the store of a held account's folders.

**The transaction shapes stay explicit in the contract, by what each family takes:**

- **Message acts and filing take the caller's transaction** in every phase, and in every phase the act commits to stored state in it with its audit entry ([axis E](#every-phase-commits-an-act-on-a-message-locally-and-a-phase-with-a-source-carries-it-afterwards)). On a mirrored and on a restoring account the same transaction opens the mutation record the converger carries to the server under ADR 0007; on a held account nothing more is written. The one act a mirrored account still records without committing is one that would create an occurrence on a server that does not name where it put it.
- **Folder acts take no transaction, and each implementation owns its own.** A mirrored folder act reaches the server first and writes the declaration and the folder row only once the server has answered, because a transaction held open across an IMAP round trip is exactly what ADR 0007's write session exists to avoid. A held folder act commits in one transaction, and asks the resolver again inside it — the one place the phase is read, now given that transaction — refusing with `AccountNotHeld` where the account no longer resolves to the held implementation since the act was dispatched. A mirrored act that races a switch to `Held` is bounded by one server round trip, and ends with a declaration a held account reads only when it is restored — the same window `MailFolderEditor` has today, named rather than closed.

**`Restoring` is a phase of its own, not a flag on the held implementation.** Its message acts commit locally, as a held account's do, and in the same transaction open the mutation record that carries the act to the source wherever the message holds an occurrence — ADR 0034's rule, unchanged. Its folder acts are refused with `AccountNotHeld` and its folder description allows none, because its local folders are still the truth while its source is being filled from them. Its filing is the mirrored path — stored locally and appended to the source through the durable record ADR 0007 governs — since the source of a restoring account is not drained. What sets it apart from a mirrored account under axis E is who wins: its local state is the truth while the source is being filled, so a refusal from the source is reported and never reverted. Writing it as its own class is what keeps that combination readable in one place instead of as conditions in two.

Option C2 was refused because three resolvers are three readers of the phase, and two acts in one request could still be judged by two of them; nine implementation classes also put one phase's behaviour in three files a reviewer must assemble. Option C3 keeps exhaustiveness and loses the rest: a helper the switches call is still six places deciding, each with its own idea of which transaction to read in, and it gives a contributor adding an act nothing to implement.

### What is not behind the port

**Synchronization, the drain, the restore, and the converger stay specific to their mode** (option D1). Each exists because of a mode rather than independently of one: synchronization imports a mirrored account's remote changes and refuses to import a held account's; the drain empties a held account's source; the restore fills a restoring account's source; the converger carries a mirrored account's mutation records and only a held account's erasures. Putting them behind the port would give the held implementation a synchronizer that does nothing and the mirrored one a drain that does nothing, and the port would grow one empty method per background pass — option D2. They keep reading the phase, and they are the only code besides the resolver that decides anything from it.

### Every phase commits an act on a message locally, and a phase with a source carries it afterwards

**A person's act on a message is one local commit on every account** (option E1). Setting or clearing `\Seen` and `\Flagged`, adding, removing, or replacing keywords, moving, copying, and deleting all write the stored state in the transaction that accepts the act, with its audit entry, exactly as ADR 0034 made them on a `Held` account. `HeldMailboxCustodian`, `MirroredMailboxCustodian`, and `RestoringMailboxCustodian` share that one commit, and what they add to it is propagation: nothing on a held account, a mutation record on a mirrored account and on a restoring one, which the converger carries to the server under ADR 0007 as it does today. The request returns when the commit lands, and the change is announced to every client of the account then — `mail.flags.changed` for a flag or a read, `mail.changed` otherwise — on every replica, over the backplane, so another device shows it without waiting for any mail server. A change completing on the server announces nothing further where the stored state did not move. Option E2 is the arrangement this reopening exists to end; option E3 still makes the person wait on IMAP, merely on a different writer.

**The phases then differ in propagation and in who wins a conflict, and in nothing else.** On a `Held` account nobody else writes the mailbox. On a `Mirrored` account the server wins once the act has completed there: what synchronization observes afterwards is written as it always was. On a `Restoring` account MailFathom wins: its local state is what the source is being filled from, so the source refusing a change holds the account in `Restoring` and is reported as ADR 0034 reports it, and nothing is reverted.

**ADR 0007's single writer is replaced by one writer per field at a time.** That record made synchronization the only writer of a mirrored account's stored `IsMarkedSeen`, `IsFlagged`, `Keywords`, and folder. Under this axis the act that commits locally writes the field, and while its change is outstanding it is the field's only writer; once the change has ended, synchronization's observation is the only writer again. The handover is the record's own lifecycle, so the two never write one field in the same period — [axis F](#a-field-with-an-outstanding-change-keeps-the-value-the-act-wrote) is how synchronization keeps to that. ADR 0039's own driver that a mirrored *folder* act reaches the server before anything is written is untouched: it governs folder acts, which stay server-first (below).

**Every requester takes the same path.** A rule's act, a spam verdict's, and an MCP caller's `set_mail_flags` reach the same port and commit locally as a person's does, because one implementation is what removes the rarely exercised branch, and because a rule pass whose later rule reads what an earlier one wrote, or an agent reading straight after it wrote, would otherwise read the state before its own act. `set_mail_flags` keeps recording rather than holding a session — ADR 0007's axis I is unchanged — and its `applied` member now reports a local commit on every account.

**Folder acts stay server-first.** Creating, renaming, moving, and deleting a folder on a mirrored account still reach the server first and write the folder row and its declaration only once the server answered, exactly as ADR 0007 axes L to N and the transaction shapes above state. A folder act is rare, made one at a time by a person, and the one place where a refusal after the fact would have to undo a hierarchy other acts have since filed mail into; none of what makes a message act worth committing first holds for it.

**Delete commits locally, and what cannot be undone waits for the server.** A deleted message leaves every listing, search, thread, and tool answer when the delete commits, and keeps its row, its payload, and everything derived from it until its change has completed on the server. Only then does `AuthoredDeleteEmailDisposition` retire it as today, so a refused delete has a message to put back. A delete on an account whose server was last observed without `UIDPLUS` is refused when it is asked for, from the [capability record](#where-the-capabilities-come-from), rather than recorded and refused later — ADR 0007 already refuses it, and the record is what lets that refusal arrive before the person sees the message go.

### A field with an outstanding change keeps the value the act wrote

**The overlay is per field, not per message** (option F1). The fields are `\Seen`, `\Flagged`, each keyword by name — a replacement committed locally first is outstanding on the keywords it changed, and one that is not has no overlay at all — and the message's place: the folder a move or a copy named, and a delete's removal from every folder. A field is *outstanding* while a mutation record that wrote it has not reached a terminal stage.

**While a field is outstanding, synchronization records and does not write.** What it observes for that field goes onto the outstanding record as the field's last observed value, and the stored field stays as the act wrote it. Every other field of the same message is written from the observation as ever, so a message flagged locally whose `\Seen` another client changed shows both. The record carries the field's last observed value from the moment it is written — the value the act replaced — so a revert always has a server value to return to, however many observations arrived meanwhile.

**The overlay is released by the record ending, and by nothing else.** A change that completes is followed by synchronization's next observation, written as ever; in the ordinary case that is the value the act wrote and nothing moves. A change that is given up has its field restored to the last observed value in the transaction that abandons the record ([axis G](#a-refusal-an-outage-and-an-answer-that-never-came)). A change superseded by a newer one hands the field to the newer record in the same transaction. So an overlay can neither outlive its record nor end without one of those three.

**A move's occurrence follows the server.** A message moved locally names its destination folder at once, while its occurrence still names the source binding and UID until the server reports where the moved message went. The destination's forward pass then meets the new occurrence, recognizes it through the record's `COPYUID` exactly as a relocation's arrival is recognized today, and binds it to the row already stored there, fetching nothing. A copy is written as a second stored message on the commit, from the source row's stored content, and bound the same way ([ADR 0008](0008-copied-message-local-identity.md)).

**Another client changing the same field is not a failure.** Before MailFathom's command reaches the server, the command is issued as recorded: IMAP does not say when another client set a flag, and the person's act is the newest intent MailFathom holds, so the value last to reach the server is MailFathom's. After the command has completed, the server wins, and another client changing the field later is an observation written like any other. Neither case reverts anything or tells anybody.

**A conflict over keywords is merged, and only where both sides change one keyword does the last one win** (issue 3145). A replacement committed locally first opens only the `RemoveKeywords` and the `AddKeywords` its difference from the stored keywords needs, measured in the transaction that commits the act, and opens nothing where there is no difference. `+FLAGS` and `-FLAGS` are atomic and name keywords, so nothing is read and nothing is retried: a keyword another client sets while the act is outstanding is left on the message, and shows locally meanwhile because the overlay holds only the keywords the act named. "Last" means last to reach the server, since IMAP records no time per keyword, so a change held back by an outage overwrites a later one made elsewhere. A replacement stays exact against the server's own set where the stored row is not the base it would need: while a replica does not know the overlay, on a `Restoring` account, and in the restore pass, where MailFathom's state is the truth. A `Held` account issues no command at all. Option F2 is the arrangement being replaced — every reader but one browser tab sees the old state — and option F3 would freeze a message's unread count, its other flags, and a move made by another client for as long as one unrelated keyword is on its way.

### Changes to one message reach the server in the order they were made

The converger reads an account's outstanding records oldest first, and that alone does not order them: a record left for a later attempt does not hold back a newer one on the same message, so a read followed by an unread, where the read was refused once and retried, ends with the message read on the server. Two rules replace that:

- **A newer change to a field replaces an older one still outstanding on that field.** The older record is withdrawn — `Cancelled`, which asks nothing of anybody — in the transaction that records the newer one, and the newer one carries the older one's last observed value forward as the value a revert returns to. So only the state the person last asked for is sent, and a read, an unread, and a read in quick succession become one `STORE`. A record whose command has already gone out cannot be withdrawn; the newer change waits for it instead, under the second rule.
- **A change that cannot replace an earlier one waits for it.** A move waits while any earlier change to the same message is outstanding or being retried, and every change waits while an earlier move of the same message is, because a move changes the occurrence the next command names; a change waiting on a move resolves the occurrence it names only when it is issued. Changes to different fields that are not moves name the same occurrence and do not wait on each other. Ordering is per message, so every other message of the account keeps converging, and once the earlier change completes or is given up the next one proceeds.

### Acts that create an occurrence are local-first only where the server names it

**A move, a copy, and an append go local-first only where the account's last observed capabilities include RFC 4315 `UIDPLUS`**, or `IMAP4rev2`, which folds it into the base protocol under RFC 9051: that is what makes the server answer a `COPY` or a `MOVE` with `COPYUID` and an `APPEND` with `APPENDUID`, naming exactly where it put the new occurrence, and that name is what binds the occurrence to the row the commit already wrote. Where `UIDPLUS` was not last observed, the act is server-first as it is today: the record is written, the stored state follows synchronization's observation, and the person waits on the server. A delete is not in this list — it creates nothing — and is refused outright there, as above.

**Where a response carries no UID anyway, the act falls back on its own, with no guessing.** A server that advertises `UIDPLUS` still answers `UIDNOTSTICKY` for a folder whose UIDs do not persist, and some folders take an append and report nothing. A sent copy and a draft then fall back on the `Message-ID` this deployment minted, read back in the folder playing their role — the one identity comparison ADR 0007 already accepts. A move or a copy has no such identity, so the server's observation wins, and the record — completed, with no placement named — is what says which row the commit wrote and which destination it went to. The destination's first forward pass after that completion stores what it discovers there as ordinary discoveries and, in the same transaction, retires the row the commit wrote; nothing tries to say which discovery that row was. For a **move**, whichever pass reaches it first decides the ending: where the source's pass sees the occurrence gone first, the disappearance is attributed to the record as today, and where the destination's pass reads through first with the row still at its old occurrence, that retirement erases the row and the record with it, so the discovery takes the message's place under its own identity. Either way the message ends in the destination under a new identity rather than in two places or in none. For a **copy**, the source occurrence and its row are untouched, and the locally written second row gives way to the discovered one, so the copy ends as one row in each folder. In both cases the discovered arrival reaches rule evaluation like any other discovery, exactly as [ADR 0008](0008-copied-message-local-identity.md) states for a copy whose placement the server did not name: withholding it is what the join does, and there is no join to do it with. This is the rare case — a server that advertises `UIDPLUS` and still names nothing — and a rule that fires on a person's own move or copy there is accepted for the same reason ADR 0008 accepts it.

**A move or a copy is read against the source first, because a server answers the command the same either way.** A `UID MOVE` or a `UID COPY` naming a UID that has gone answers `OK` having moved nothing — checked against Dovecot 2.4 and GreenMail 2.1, the first naming no placement and the second answering a `COPYUID` with empty sets — and no later reading can tell that from a move into a `UIDNOTSTICKY` folder, which names none either. `MODSEQ` and `UNCHANGEDSINCE` guard only `STORE`, and a move needs no version check: a moved message leaves its UID behind, so the UID is the version and another client moving it first simply wins, the opposite of how a keyword race ends. So the session issues a `NOOP`, because a selection opened earlier still answers a `FETCH` for a message another client expunged until the server has been given a command to say so, then a `UID FETCH` of that UID, immediately before the command. A message that is not there ends as the [permanent refusal](#a-refusal-an-outage-and-an-answer-that-never-came) that a message no longer at its occurrence is: on a mirrored account the row goes back and the person is told, a copy's second row is erased, and on a restoring account it is reported and reverted nowhere. A message that leaves in the one round trip between the reading and the command completes as it always did.

**A flag, a keyword, or a delete aimed at a UID that has gone completes having done nothing.** `UID STORE` and `UID EXPUNGE` answer `OK` for it on both of those servers and nothing here reads first, so nothing is reverted and nobody is told. Somebody has moved or removed the message; if moved, the message is what the forward pass of the folder it went to discovers, in the state that server holds, and a delete leaving it alive there is a defensible ending for a delete that raced a move.

### Where the capabilities come from

**Each account carries the capabilities its server last advertised after authentication, with the instant they were observed** (issue 2742). Every authenticated session against the source writes it — synchronization, the write session, push, a held account's drain and a restoring account's restore — and two replicas writing at once resolve by the later observation. An account whose server was never reached reads as advertising nothing, so its acts are server-first until a session has said otherwise. It is the advertisement after login rather than before because servers list far less before authentication, and it is refreshed by every session rather than probed once when the account is created because a server is upgraded, migrated, or reconfigured underneath an account that stays. One application port reads it, and only the custody resolution path and the write session consume it: a custodian deciding at the moment of an act has no IMAP session open and must not open one.

### A refusal, an outage, and an answer that never came

**A refusal is the server answering a command and not taking it** (option G1), and it has two classes:

- **Permanent** — retrying cannot help. The message is no longer at its occurrence, including a server that returns under a new `UIDVALIDITY`; the destination folder is gone (`NONEXISTENT`, `TRYCREATE`); the act is not permitted (`NOPERM`, `CANNOT`, `READ-ONLY`, `CONTACTADMIN`); the folder will not keep the keyword (`PERMANENTFLAGS`); the server no longer advertises what the act needs; or the server answered `BAD`, which names a command MailFathom should not have sent. A permanent refusal ends the change at the first refusal.
- **Transient** — the server may take it later: `UNAVAILABLE`, `INUSE`, `LIMIT`, `OVERQUOTA`, `SERVERBUG`, a `NO` with no response code, and any code this list does not name, because one more attempt is cheap and the window bounds it. A transient refusal is retried on the converger's passes and ends no later than **`MailSynchronization:MutationRefusalWindow`** after the first refusal, fifteen minutes by default. That one setting holds the bound and replaces `MailSynchronization:MaxMutationAttempts`, and startup refuses a value that is not positive. The deadline is enforced by the account's supervision without opening a connection, so neither a backoff nor an outage that follows a refusal defers it.

**The classes are read from what the mail library reports, and that is coarser than the response codes above.** MailKit reads a tagged response's code into a type it does not publish and hands the caller the server's text with the code taken out, so the write session can tell `BAD` from `NO`, a folder the server reports gone (`NONEXISTENT`, `TRYCREATE`), and a folder it holds open read-only (`READ-ONLY`), and it cannot tell `NOPERM`, `CANNOT`, or `CONTACTADMIN` from a `NO` with no code. Those three are therefore classed transient: such a change is asked again and given up once the window passes rather than at the first refusal, and its notification offers *Ask again*. Reading the codes would take a protocol logger parsing every server line on the write connection, or MailKit publishing the code; until one exists, fifteen minutes is the cost of the coarser reading, and no change is given up on any sooner than a permanent refusal would have it.

**A refusal is reverted when the change is given up, and the person is always told.** While a transient refusal is being retried, the change stays as the person made it, marked nowhere. Once the change is given up, the deployment — never the client — restores each field it wrote to its last observed value in the transaction that abandons the record, announces the change to every client as it announced the act, and raises a notification. A transient refusal's notification offers *Ask again* — *Move again…* for a move — which records the change again under a new record, committed locally at once; a permanent one explains and offers no retry. A conflict with another client is not a refusal: nothing is reverted and nobody is told.

**An outage is not a refusal.** A server that cannot be reached, a connection that cannot be established, TLS that cannot be negotiated, a timeout before a command was written, a greeting of `BYE`, and the account's open circuit count no attempt and revert nothing; an authentication failure is the account's own failure, reported as it is today, and counts nothing against a change either. Changes wait in MailFathom however long the outage lasts, because the person still wants them made once the server is back, and no notification is raised for one. A change is undone only when the server answers and refuses it — which includes a server that returns without the message or under a new `UIDVALIDITY`, and then it takes the permanent path above. Option G2 was refused because it abandons, and under local-first would revert, every change made during an hour's outage although nothing refused any of them, while a change the server keeps refusing takes an hour and more to be given up; option G3 would revert a change because a server was down.

**A command with no answer is settled without asking the person.** A flag, a keyword, or a delete whose answer never came is asked again on the next pass rather than read off the next observation: the store, the flag change, and the `\Deleted` mark are idempotent on the server, so asking twice converges on the one value the person chose, and a connection that dropped before the answer counts as the outage it was rather than as a refusal. A server that then refuses it starts the change's window like any other refusal. A placement whose answer never came keeps the settlement the converger already gives it from what the source and destination folders show, and never issues an `APPEND` twice — ADR 0007's rule for an append stands unchanged, and an append left unknown is never retried.

### What a person is told, and where

- **In sync means in MailFathom.** A change MailFathom holds is shown as made. No message, row, or toast marks a change that has not reached the mail server yet, and the client's pending-change tracking gives way to that rule (issue 2747). A person hears about the mail server only when something failed, or in the one place below.
- **The account freshness line at the foot of the folder column** is that one place. It turns the account *not current* once the account has been unreachable for 60 seconds, once a change has waited 60 seconds, or once the account has been behind for 60 seconds. Its details, opened by pressing the line, say for an outage that the mail server is unreachable, since when, how many changes are waiting, and that they are kept in MailFathom and will reach it when it is back. It clears on its own when the server is back. What the deployment owes it is on the client API's account list: the account's `Unreachable` state and since when it has held, since when the account has been in its current synchronization state and since when it has been behind, how many changes MailFathom holds that have not reached the mail server, and when the oldest of them was committed. Sends are not counted there. No setting holds an outage notification's delay or repeat, because there is no such notification.
- **A refusal reaches the person within fifteen minutes**, for a flag, a read, a keyword, a move, a delete, and a send alike: a permanent refusal at the first one, a transient one no later than fifteen minutes after the first refusal. Issue 2744 builds it for mailbox changes and issue 2749 for sends.

### Sending, sent copies, and drafts

**A send is not local-first.** It stays in the outbox, shown as waiting, trying again, or sending, until the submission server actually accepts it. Only then does it leave the outbox, its sent copy is filed, and its stored MIME is released (issue 2739); nothing shows a message as sent, or puts it in Sent, before that acceptance. Sends are the exception to the outage rule as well: a message is time-sensitive and already has its own record in the outbox, so a send that cannot reach its submission server is shown as not sent no later than fifteen minutes after its first failed attempt, outage or not (issue 2749, under [ADR 0040](0040-each-account-outbox-as-a-read-only-list-beside-its-folders.md)).

**On a mirrored account whose server was last observed with `UIDPLUS`, a sent copy and a draft are filed locally first** (issue 2745). The sent copy is a stored message in the folder playing the sent role, written from the outgoing bytes in the transaction that settles the delivery where `Delivery:FileSentCopy` holds; a draft revision is a stored message in the folder playing the drafts role, written in the transaction that saves it. Each is announced when it commits. The append follows through the durable record ADR 0007 governs, and synchronization binds the server's occurrence onto the row already stored — from `APPENDUID`, or by the minted `Message-ID` where none came back — without fetching the body and without a second row. An append that never answered leaves the local row as the record of the send and is never repeated. Without `UIDPLUS` filing stays as ADR 0007 wrote it: appended, then downloaded back and recognized.

**Where the provider files its own sent copy as well, MailFathom's copy is kept and the provider's is removed.** This reverses `Delivery:WithdrawDuplicateSentCopy`, which withdraws MailFathom's appended copy, because MailFathom's local copy exists first, so rules, derivations, and AI acts may already have worked on it, and a second row arriving later would be processed again. The provider's copy is recognized by the `Message-ID` this deployment minted for an outgoing record of the same account, met in the folder playing the sent role, and it is intercepted as synchronization meets it: no row is stored for it, and it reaches no rule, spam classification, cut, embedding, or derivation. It is removed from the server — `UID STORE +FLAGS (\Deleted)` and `UID EXPUNGE` naming its UID alone, through the write session — only where removing a message MailFathom did not compose is safe, which is all four of: MailFathom's own append was answered; its occurrence is bound by `APPENDUID`; the server advertises `UIDPLUS`; and the provider's copy was met within the fifteen minutes the withdrawal uses today, before another client is likely to have acted on it. Where MailFathom's append never happened or never answered — `Delivery:FileSentCopy` off, an unanswered append — the provider's copy is the only one on the server, so the local row binds to it instead. Past the window, both stay on the server and the provider's copy is stored as a second row, because a mirrored account shows what its server holds. Where the server reports that its folders are labels over one store (`X-GM-EXT-1`), nothing is removed — an expunge there takes a label off a message rather than the message — and `Delivery:FileSentCopy: false` is the posture ADR 0007 already names for such a provider.

### Filing a message into a folder of another account

A mail server moves a message only between folders of one account, so carrying one to another account is an append on the destination and a removal from the source — two acts against two servers, under two accounts' leases and write connections. Under option E1 the person's half is still one local commit (option H1):

- **One commit, two records, each account its own.** The commit writes a new stored message on the destination account in the destination folder, takes the source row out of every listing exactly as a delete does, and records two mutation records: an **append** on the destination account, carrying the stored bytes, and a **removal** on the source account, `UID STORE +FLAGS (\Deleted)` and `UID EXPUNGE` naming the source occurrence alone. Each is converged by its own account's converger, under its own lease, over its own write connection, so every record still belongs to one account and no converger reaches a second account's server. Option H2 was refused because a record converged across two accounts needs two leases and two connections held by one pass, which is exactly the exclusion ADR 0031 gives an account, split.
- **The append lands before the removal is issued.** The removal is not eligible until the append it is recorded beside has completed, and a carrying that half succeeded therefore leaves the message in two mailboxes and never in none.
- **A half success is reported, never left.** An append that completed beside a removal that was given up leaves both servers holding the message: the source row is restored, exactly as a refused delete restores one, the destination keeps its copy, and the notification says the message is now in both accounts. An append that was given up reverts the whole act like any refused move: the destination row is erased, the source row shows again where it was, and the removal is withdrawn before it was ever issued. An outage on either side holds both halves in MailFathom, as for any change.
- **The destination copy is a new stored message of the destination account** ([ADR 0008](0008-copied-message-local-identity.md)), with its own identifier, its own payload written from the source row's stored bytes, and its occurrence bound from `APPENDUID`. Nothing derived is carried across: derived data inherits the constraints of the account the mail came from, so the destination derives its own extracted text, passages, and embeddings under its own account's profile and folder settings, and the source's go with the source row when its removal completes and the row is retired. The arrival is MailFathom's own filing, so it is withheld from rule evaluation and from spam classification as ADR 0008 withholds a copy MailFathom performed: the person placed it, and a verdict over it would be a second opinion nobody asked for.
- **Every pairing of custody phases is stated.** *Mirrored to mirrored*: an append record and a removal record, as above. *Mirrored to held*: the destination is a local commit with no record, and the source has its removal record. *Held to mirrored*: the destination has its append record, and the held source row is erased only once that append has completed — with a source removal record, under ADR 0034's rule for an erasure, where the source still holds the occurrence. *Held to held*: one transaction writes the destination row and erases the source row, and nothing converges but such a source removal record. A *restoring* account on either side is refused, because its local state is still the truth its source is being filled from and its folder acts are refused for the same reason.
- **What is refused is refused with a sentence, before anything is recorded**: either side mirrored and last observed without `UIDPLUS`, since the destination needs `APPENDUID` and the source `UID EXPUNGE`; either side restoring; a person who may read but not move mail on either account, since the act needs `mailfathom.mail.move` on both; a source message filed from an outgoing record — a sent copy or a draft — whose join to that record holds only on its own account; and a destination folder playing the drafts or sent role, which hold what an account's own outgoing records filed, so a message from another account there would read as one this account composed or sent.
- **Only the person asks for it, through the client.** A rule belongs to one account's configuration and names destinations by alias in that account, a spam verdict files into the account's own junk, and an MCP caller authors only the flag tier under ADR 0007 axis I. Option H3 was refused because where a message belongs should not be decided by which mailbox it arrived in, and local-first is what makes the act one gesture rather than two the person has to sequence by hand.

### Rules, spam verdicts, and MCP callers, and what waits for the server

A rule's, a spam verdict's, and a caller's acts are local-first like a person's (above). **Nothing irreversible is done on the strength of an act the server has not confirmed.** The only irreversible local consequence of a message act is a delete's retirement, and on a mirrored account it waits for the delete to complete on the server; a held account's erasure is its own act with its own grace window under ADR 0034. A revert fires no rule and is not an arrival, so nothing is triggered by state coming back. An act another requester took on state that was later reverted — a rule filing a message the person had flagged, an agent's answer composed from it — stays as it was: each of those acts is itself reversible, and the person is told about the change that was reverted. Rules evaluate arriving mail rather than a person's acts, so the case of a rule reacting to a person's unconfirmed act does not arise.

### The never-marks-read guarantee

**The read path stays incapable of opening a mutation record, as a property of its types.** Committing locally first is done by the custodian's message acts, and the custodian is a port no read path holds: synchronization, reconciliation, content retrieval, and every MCP tool that reads depend on neither the custodian nor the write factory, exactly as ADR 0007's axis B arranged, so no read can write a stored `\Seen` or open the record that would carry one to the server. The `\Seen` regression test and `MailboxCustodyBoundaryTests` keep holding it, and the overlay changes nothing about it: synchronization recording an observation onto an outstanding record is a write to MailFathom's own bookkeeping, never a command to a server.

### A rolling upgrade

**Local-first is enabled only once every replica runs a build that knows the overlay**, because an older replica's synchronization writes every observation and would write over a field a newer replica's act left outstanding. A build that knows it says so in the work-lease holder stamp ADR 0034 introduced, with a marker of its own read exactly as that record reads the build — its presence is the statement, and no version is compared — and the mirrored custodian commits locally only while every live work lease carries it, taking today's server-first path otherwise. So during a rolling upgrade a change is server-first, and after it local-first, without an operator switching anything. The residue is bounded rather than closed: a replica that holds no lease is invisible to the check, and an older replica that takes a lease after an act committed writes the server's value over that field until the change completes and its observation brings the act's value back — a stale view for at most one convergence, never a lost act, since the record still carries the change. The schema it needs is additive: the overlay's last observed values, the capability record, the link between the two halves of a carrying across accounts, and the idempotency key every mailbox-act route on the client API takes (issue 2743), which no older build reads.

### Where the converger runs

**This record does not decide it, and defers that one point to the measurement on issue 2740.** Today the converger is a stage of the account's synchronization run, and a run already under way answers a recorded change at its next stage boundary, so the delay before the server has a change is bounded by the longest stage of a running run. Under local-first that delay is no longer anything a person waits for in MailFathom; it is the time before every other client of the same mailbox — a phone, a desktop mail client — sees the change. Whether that is short enough, or whether the converger leaves the run for a worker of its own, is decided from what issue 2740 records — `mailfathom.mailbox.mutation.convergence_delay`, the wait from a change's record being written to its ending, whose `completed` half is the wait before the mail server had it, and `mailfathom.mail.filing.sent_copy_delay` beside it for a sent copy, both described in [telemetry](../operations/telemetry.md) — once a deployment has run with them long enough to read, and this record is amended with the figure and the answer then. Until it is, the converger stays where it is, and the refusal window above is enforced without a connection precisely so that its bound does not depend on the answer.

### Risks, and what each one is met with

1. **The overlay diverging from the server** — a field overwritten while outstanding, or an overlay never released. Met by tying the overlay to the record's own lifecycle: it exists while a record that wrote the field is not terminal and at no other time, so it ends with the record by construction, and every record ends — completed, given up within the refusal window, superseded, or settled by observation. Synchronization records rather than writes for exactly those fields, and tests hold a conflicting observation against an outstanding field.
2. **A rolling upgrade's older replica writing over local-first state.** Met by enabling local-first only while every live work lease carries the overlay's marker; the residue — a replica with no lease, or one taking a lease after an act — is a stale view for one convergence and never a lost act, and is accepted as such.
3. **A change a person saw being reverted.** Met by reverting only on a refusal the server actually answered, never for an outage however long, and always telling the person why, within fifteen minutes and with *Ask again* where retrying can help. That a change can still come back is the accepted cost of showing it at once.
4. **A rule or an agent acting irreversibly on state that is later reverted.** Met by deferring the one irreversible local consequence — a delete's retirement — until the server has completed the delete; everything else a rule or an agent can do is reversible, and an answer composed from reverted state is accepted as the answer it was.
5. **A read path opening a mutation record and marking mail read on the server.** Met by the types: no read path holds the custodian or the write factory, and the boundary tests and the `\Seen` regression test fail on a component that does.
6. **An unknown outcome after a crash between a command and its answer.** Met by settling it from the next observation without asking the person, by resuming a placement from the stage its record names, and by never issuing an `APPEND` twice.
7. **Another client changing the same field before the act reaches the server.** Accepted: the value last to reach the server is MailFathom's, because IMAP does not say when the other client acted and the person's act is the newest intent MailFathom holds. Nothing is reverted and nobody is told, and after completion the other client's later change wins as an observation.
8. **A server that returns no UID.** Met by going local-first only where `UIDPLUS` was last observed, and, where a response names nothing anyway, by the minted `Message-ID` for a sent copy and a draft and the server's observation for a move or a copy — never a guess. A capability record gone stale underneath an act ends in that same fallback.
9. **Other clients still seeing the change only once it has converged.** Accepted for now, and measured: the delay is what issue 2740 records, and where the converger runs is decided from it.
10. **A carrying across two accounts that half succeeded, leaving the message in both mailboxes or in neither.** Met by ordering the halves — the removal is issued only once the append has completed, so *in neither* cannot happen — and by reporting *in both* to the person, saying which half failed, rather than leaving it.

### What ADR 0007, ADR 0008, and ADR 0034 keep, and what this record changes

All three records are `proposed`, so for issue 2577 each was left as written and given a pointer to this one rather than being superseded.

- **ADR 0034** keeps everything it decided about holding a mailbox — the switch, the phases, the drain gate, local acts, the five protected roles, background source work, filing, export, and the operator's obligations. This record replaces two of its sentences. *A stored message also carries the local folder it is in, which on a mirrored account is the folder its occurrence is in and on a held account is MailFathom's own* becomes [a stored message names exactly one folder](#every-account-has-folder-rows-and-a-stored-message-names-exactly-one-of-them), for every account. *The choice of executor is made once, in the mutation layer, from the account's phase* becomes [one resolver for every act](#every-act-on-a-mailbox-goes-through-one-contract-implemented-once-per-custody-phase) — folder acts and filing as well as message acts, which is what the sentence promised and the code did not deliver.
- **ADR 0007** governs every command MailFathom issues against a source server unchanged, axes L to N included: which folder acts reach a mirrored account's server, for which requester, under which permission, and that a declaration is written only after the server acted. What changes is the identity a surface names such a folder by — its `MailFolderId` rather than its alias — and that the act writes the folder row's projection beside the declaration. The alias still never moves; it has stopped being what anybody outside configuration reads.
- **ADR 0008**'s first clause, that a copy is a second stored message, holds; its second clause was already replaced by ADR 0034. This record adds only that the message's folder is a reference of its own rather than a component of its occurrence.

The reopening on issue 2741 goes further, and the owner approved amending the three records in place for it rather than pointing at this one from beside them. So each of their sentences that axes E to H made untrue is corrected where it stands, and each names this record as the place the change is decided:

- **ADR 0007** loses its single writer: a person's act writes a mirrored account's stored field, and synchronization stops writing a field while a change on it is outstanding. Its kinds of mutation, the write session, the never-marks-read boundary, and the caller-authored tier are unchanged, and so is every command it governs but two bounds it now widens and reviews in its own § *The authorization review the local-first reopening required*: its append, which admitted only a message MailFathom composed, also carries a message filed into another account, and its delete is also issued by the deployment against a provider's own sent copy. What changes besides is when the stored value moves, how a change the server will not take ends, the order changes to one message reach the server, and, for a sent copy, which of two copies is kept.
- **ADR 0034** keeps its `Held` phase exactly as it is. Its option D1 — the act commits to stored state in one transaction — is now what every phase runs, and its sentence that a mirrored account's stored flags have reconciliation as their writer becomes the one writer per field at a time above.
- **ADR 0008** keeps a copy as a second stored message. A copy made locally first is written from the source row's stored content and bound by `COPYUID` rather than discovered, and a message filed into another account is a new stored message of that account.
- **[ADR 0026](0026-marking-a-message-read-when-a-person-opens-it-in-the-client.md)** is not amended, and one premise of it no longer holds as written: its driver that `\Seen` has one local writer, the stored flag being an observation of the server and never an instruction, rested on ADR 0007's single writer. One writer per field at a time replaces that premise. What the driver protects stays true — there is never a second, MailFathom-only read state beside the server's, because the overlay lasts only until the change it carries has reached the server or been given up — and a message marked read on opening is one more local-first `\Seen` change under axis E.

### What breaks, and what each party does

The major version is `0`, and [ADR 0004](0004-versioning-and-release-policy.md) permits a minor to break any of the four public surfaces. Three of them break; the configuration schema does not.

- **The MCP tool contract.** The `folders` argument of `list_emails`, `search_emails`, and `ask_mail` takes a folder identifier or a role written as `role:<Role>`, and refuses an alias with the refusal an unknown folder already gets. Every result that reports `folderAlias` — a listed summary, a cited email, retrieved content, the `set_mail_flags` result, and each folder's freshness in `list_accounts` — reports the folder's `folderId` and its `folderPath` instead, and `list_accounts` lists each account's folders with identifier, path, and role, which is where a model learns the identifiers. **Caller's action**: an agent prompt, a saved tool call, or an integration that names a folder by alias names it by role, or reads its identifier from `list_accounts`. Nothing changes on the deployment.
- **The client endpoint.** The folder tree served at `/folders` and the folders served at `/managed-folders` name every folder by its `MailFolderId`, on every account in every phase, so a folder one returns is the folder the other acts on. The folder scope of the timeline and of search, the destination of a move, the folder fields of a message, a citation, a mutation, and a spam verdict, and the signals announcing a changed folder use it too. **Operator's action**: none beyond deploying the release, because the web client is served by the deployment it talks to; a desktop or Android client older than the release fails every folder call until it is updated, and the release notes say so.
- **The database schema**, expanded in one release and contracted in a later one. The first adds the folder rows of every mirrored account and the new reference on every stored message, backfills both — on a mirrored account a folder for each alias a binding names, on a held or restoring account its existing local folders under the identifiers they already carry, and each message's folder from its local folder where it has one and from its binding otherwise — keeps the old columns written by the new build, and carries what an older build writes into the old columns onto the new reference in the same statement, so two builds against one database never disagree about which folder a message is in. The later release removes the old columns and that carriage. Neither regenerates a baseline. **Operator's action**: apply the release's schema artifact as for every release, and plan for the expanding migration taking time in proportion to the stored mail, since it writes every stored message once; install the contracting release only over the expanding one, and only once no replica runs an older build — its changelog entry names the release it requires.

The administrative surface and `mfctl` accept a folder identifier wherever they accept an alias today, and keep accepting the alias, because an operator works from the configuration they wrote and a held account's own folders have no alias to name them by. That is two names for two audiences rather than a compatibility path. Audit entries keep naming folders by path, as ADR 0034 already requires.

Axes E to H break three surfaces again, each in the release that builds the part that breaks it, and the database schema only grows:

- **The configuration schema.** `MailSynchronization:MaxMutationAttempts` is replaced by `MailSynchronization:MutationRefusalWindow`, a duration defaulting to fifteen minutes (issue 2744). `Delivery:WithdrawDuplicateSentCopy` is replaced, because its meaning — withdraw MailFathom's copy and keep the provider's — is the one reversed (issue 2745). **Operator's action**: remove both keys; a deployment that set the attempt count sets the window instead, and one that turned the withdrawal off to keep both copies sets `Delivery:FileSentCopy: false` where the provider files its own.
- **The MCP tool contract.** `set_mail_flags`' `applied` member reports a local commit on every account, so a read straight after it returns what was set (issue 2743). **Caller's action**: an integration that polled after the call until the value appeared stops polling.
- **The client endpoint.** Every mailbox-act route takes an idempotency key the client generates once per act, and the account list carries the freshness line's fields (issues 2743 and 2744). **Operator's action**: none beyond deploying the release, for the reason above; a desktop or Android client older than it fails those routes until it is updated, and the release notes say so.
- **The database schema** gains the capability record, the overlay's last observed values, the link between a carrying's two records, and the idempotency keys, each in an additive migration that no older build reads.

### Consequences

- Good, because a held account's folders and moves are visible to every reader, and a reader written later is correct for every phase without knowing about custody.
- Good, because the phase is read for acts in exactly one place, and both a new act and a new phase are compiler errors until they are handled everywhere they must be.
- Good, because a folder keeps one identity across a drain and a restore, so a mailbox switched on and off again is the same mailbox to every client and every tool.
- Good, because each phase's behaviour reads in one class, and a reviewer reading what a held account does follows one file instead of six dispatchers.
- Neutral, because a mirrored account gains rows that are a projection of what it declares and the server reports, which synchronization now maintains beside the bindings; the bindings and their generations are unchanged.
- Neutral, because configuration still names folders by alias, so a folder with no alias is reachable from configuration only by the role it plays, as it is today.
- Bad, because the MCP tools, the client endpoint, and the schema all break in one release, and every integration that hard-coded an alias rewrites it.
- Bad, because the schema change spans two releases with carriage between the old columns and the new reference, which is machinery that exists only for the length of an upgrade.
- Bad, because the expanding migration writes every stored message once, which on a large deployment is a migration measured in minutes.
- Good, because a person's act is visible everywhere in MailFathom the moment it commits, on the phase almost every account is in, and search, `ask_mail`, the MCP tools, and every other device agree with the tab that made it.
- Good, because one local commit runs on every account, so the held path is exercised by every account rather than by the few that hold their mailbox.
- Good, because a sent copy and a draft are stored once rather than appended and downloaded back, so a send costs one transfer of the message rather than two.
- Good, because an outage loses and reverts nothing however long it lasts, and a refusal reaches the person within fifteen minutes instead of the hour and more an attempt count took.
- Neutral, because a field now has two writers over time — the act while its change is outstanding, the observation otherwise — and which one it is follows the record's lifecycle rather than the phase alone.
- Neutral, because where the converger runs is left to issue 2740's measurement, so how long other clients wait for a change is unknown until it lands.
- Bad, because a person can watch a change come back. A refusal reverts something they saw, and the notification that says so is the price of having shown it at once.
- Bad, because a server last observed without `UIDPLUS` keeps moves, copies, and filing server-first, so that account still waits on IMAP for them — the same feature difference ADR 0007 accepts for relocation without `UIDPLUS`.
- Bad, because a rolling upgrade's older replica can still show a stale value for one convergence, and a replica with no lease is invisible to the check that prevents most of it.
- Bad, because removing a provider's own sent copy is MailFathom expunging a message it did not compose. It is bounded to four conditions and one identity this deployment minted, and it is still a new kind of removal.

## Pros and Cons of the Options

### A2 — an immutable alias for every folder

Generate an alias for every folder MailFathom creates, and make the alias the identity everywhere.

- Good, because the alias already is the identity on a mirrored account, so the read side would change least.
- Bad, because an alias reads as a name and does not follow one: after a rename it misleads a person in the client and a model in a tool call, and a model told to file into a name files into it.
- Bad, because a generated alias for a held folder is an identifier dressed as a name, which is A1 with the drawback of looking meaningful.

### A3 — both identities behind a reference that is either

Keep the alias on a mirrored account and the local identifier on a held one, and let every surface accept a text that is one or the other.

- Good, because it needs no migration.
- Bad, because every reader has to know which kind a reference is on which account, which is the defect itself, and a folder changes identity when its account changes phase.

### B2 — folder rows only on held accounts

- Good, because a mirrored account's storage is unchanged.
- Bad, because every reader unions bindings and local folders by phase, and a reader written later that does not is the next defect of this kind.

### B3 — a view over both tables

- Good, because readers query one relation.
- Bad, because it hides two writers with two identities under one name, and a stored message cannot hold a foreign key to a view.

### C2 — one contract per act family

- Good, because each contract is small and a caller depends on only the family it uses.
- Bad, because three resolvers are three readers of the phase, and one phase's behaviour is spread across three classes.

### C3 — exhaustive switches through one helper

- Good, because it is the smallest change and the compiler checks each switch.
- Bad, because the decision is still made in six places, each choosing its own transaction to read the phase in, and a new act has nothing to implement.

### D2 — background work behind the port as well

- Good, because the phase would be read in one place without exception.
- Bad, because each mode-specific pass would become an empty method on the other phases' implementations, and the port would describe what modes are rather than what a caller may ask.

### E2 — stored state follows the server's observation

- Good, because it is what is built, and a stored field has one writer for its whole life.
- Bad, because the phase almost every account is in is the one where a person's change is invisible to every reader but the tab that made it, and the held path stays the branch few accounts exercise.

### E3 — the converger writes stored state once the command is answered

- Good, because the stored value never shows anything the server has not taken.
- Bad, because the person still waits on IMAP, only for a different writer, and the converger becomes a second writer of fields synchronization also writes.

### F2 — synchronization writes as today, and the client covers the gap

- Good, because synchronization is unchanged.
- Bad, because only the browser tab that made the change sees it; search, the MCP tools, `ask_mail`, and every other device read the old state, which is the defect this reopening exists to remove.

### F3 — withhold every observation of a message with any change outstanding

- Good, because one flag per message is simpler than one per field.
- Bad, because a message with one keyword on its way would freeze its read state, its other flags, and a move another client made, for as long as that keyword waits.

### G2 — an attempt count

- Good, because it is what is built and needs no classification.
- Bad, because an attempt is counted before the connection is opened, so an hour's outage abandons every change made during it — and under local-first reverts them — while a change the server keeps refusing takes an hour and more to be given up.

### G3 — a deadline from the act itself

- Good, because it bounds every change the same way, whatever happened.
- Bad, because it reverts a change for an outage, which the owner refused: nothing refused it, and the person still wants it made.

### H2 — one record carried across both accounts

- Good, because the act is one record and its two halves cannot drift apart.
- Bad, because one pass would need two accounts' leases and two write connections at once, which splits the exclusion ADR 0031 gives an account and puts a converger on a server its account's supervisor does not hold.

### H3 — no filing across accounts

- Good, because it adds no act and no failure of its own.
- Bad, because where a message belongs is decided by which mailbox it arrived in, and the person is sent to another mail client to change that.
